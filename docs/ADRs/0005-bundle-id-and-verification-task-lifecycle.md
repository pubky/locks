# ADR 0005: Bundle IDs and verification task lifecycle

- **Status**: Accepted
- **Date**: 2026-05-28

## Context

Viewers submit proof bundles asynchronously. The product needs a durable viewer-held recovery handle for credible exit and a short-lived task model for polling verification progress.

## Decision

Bundle ID:

- Generated by the content viewer.
- 128 bits of cryptographic randomness.
- Encoded with the Rust `base32` crate using the Crockford alphabet.
- Fixed length: 26 characters.
- Canonical form is uppercase output from `base32::encode`.
- No prefix.
- No Crockford checksum.
- Parsing uses `base32::decode` with the Crockford alphabet, including that crate's built-in lowercase and ambiguous-character normalization.
- Parsing rejects hyphens/readability separators.
- Treated as a bearer secret and safe path segment after validation.

Verification task lifecycle:

- Verification is asynchronous.
- Task IDs are server-generated UUID v4 values serialized as canonical lowercase hyphenated UUID strings.
- Task IDs are distinct from Bundle IDs in both meaning and format.
- Task IDs are operational identifiers only, not bearer secrets, durable recovery handles, or credible-exit handles.
- Minimal statuses are `pending`, `in_progress`, `completed`, `failed`, and `expired`.
- Task state is stored in Lock Server private storage.
- Relevant task status is exposed to the content viewer and content creator.
- Task state is retained for a few hours.

Failed verification attempts:

- Failed attempts do not create entitlement records.
- Failed attempts are kept only in operational logs.
- No specific log retention period is required by the domain model.
- Verification submission is protected at the HTTP admission boundary by a configurable process-local in-memory fixed-window rate limit.
- The current limit applies only to `POST /proof-bundles` and is keyed by client network address and content creator, not by Bundle ID.
- Default runtime config is `[rate_limits.verification_submission] enabled = true, max_requests = 60, window_seconds = 60`.
- Exceeded limits return the stable API envelope `429` with error code `rate_limited`, message `rate limit exceeded`, and `Retry-After` set to the remaining fixed-window time in seconds.

## Consequences

Positive:

- Bundle ID remains a durable recovery handle without doubling as an operational task ID.
- Verification progress can be polled without exposing Lock Server internals.
- Failed verification data is kept out of creator-owned entitlement storage.

Negative:

- The Lock Server must maintain local task state for a few hours.
- Operators must configure rate limits appropriately for abuse resistance; the current process-local limiter resets on restart and does not coordinate across multiple Lock Server processes.
- Logs may be insufficient for long-term audit unless an explicit audit feature is added later.

## Open Follow-ups

- Define API response shapes for task status visible to content viewers and content creators.
